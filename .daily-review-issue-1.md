## O defeito

`scripts/lib/continuo-tick-closure.ts:199-213` (`rescueOrphanedWork`) devolve `{ outcome: "rescued", checkoutBackFailed: true }` quando o `git checkout master` pós-rescue falha — e a própria mensagem diz que "o checkout compartilhado ainda está na branch de rescue; trocar manualmente antes de qualquer outra sessão continuar".

Mas o CLI `scripts/rescue-continuo-orphaned-work.ts:96-115` (`main()`) só ramifica por `result.outcome`. Todo `"rescued"` vira `process.exitCode = 0` (sem `--push`, ou com `--push` bem-sucedido), imprimindo `✔ Trabalho órfão recuperado`. O campo `checkoutBackFailed` nunca é lido por nenhum consumidor.

Isso contradiz o contrato escrito na docstring do próprio script (linhas 25-33): "Este script FALHA ALTO de propósito nesses casos (#7130, direção 2 da issue: 'um tick que produziu diff e não fez nem uma coisa nem outra deveria falhar alto, não terminar em silêncio reportando sucesso') — quem chama este CLI (o Passo 0 do loop do contínuo) deve tratar exit 1 como bloqueio".

## Cenário de falha

1. Tick do contínuo deixa a árvore suja no checkout compartilhado.
2. Passo 0 de `/diaria-continuo` roda `npx tsx scripts/rescue-continuo-orphaned-work.ts`.
3. O rescue commita em `continuo/rescue-*`, mas o `git checkout master` seguinte falha (arquivo não-mesclável na árvore, lock do OneDrive, `index.lock` concorrente).
4. Script sai **0**. O Passo 0 segue em frente; `scripts/sync-code.ts` e o restante do tick rodam com o checkout compartilhado **na branch de rescue, não em master**.
5. Todo o trabalho do tick seguinte é commitado/PRado a partir da branch errada — exatamente a classe de contaminação de checkout compartilhado que o #7130 existia para prevenir.

## Correção

Em `main()`, no ramo `outcome === "rescued"`: se `result.checkoutBackFailed`, escrever no stderr e `process.exitCode = 1` **antes** de qualquer retorno 0 (inclusive no caminho sem `--push`).

## Prioridade

P2: não corrompe publicação nem dado de leitor (por isso não é P0/P1), mas quebra em silêncio a precondição de branch do loop autônomo do contínuo, e o resultado (PR aberta a partir da branch errada) exige triagem manual. O operador só descobre pelo texto no stderr, que o exit 0 convida a ignorar.

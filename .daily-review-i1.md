## Achado (review consolidado diário, range 11c201b7c..2656e4c3e)

O fix do #8668 ("preservar URLs do corpo completo antes de truncar newsletter", commit `f96ce29e0`) grava `urls_extraidas` em `CapturedThread` (`scripts/fetch-newsletter-threads.ts:254`, extração em `:240`), mas **nenhum consumidor lê esse campo**:

```
$ grep -rn "urls_extraidas" scripts/ test/
scripts/fetch-newsletter-threads.ts:64
scripts/fetch-newsletter-threads.ts:254
```

`processThreads` (`scripts/capture-newsletter-urls.ts:149-151`) continua extraindo URLs de `thread.body` — o corpo **já truncado** em `BODY_LIMIT`. O campo é gravado no JSON e descartado; as URLs do fim de newsletters longas seguem fora do pool, exatamente o sintoma que a issue descreveu.

O teste adicionado no PR (`test/capture-newsletter-urls.test.ts`) exercita a extração dentro de `fetchThread`, não o caminho ponta a ponta até `processThreads` — por isso o gap passou pelo gate leve.

## Correção esperada
`processThreads` (e demais consumidores de `captured-newsletters.json`) deve usar `thread.urls_extraidas` quando presente, mantendo canonicalização/dedup atuais, com teste de regressão ponta a ponta (corpo >BODY_LIMIT com link só no final → URL chega em `articles`).

# Mecanismo de publicação da página do acervo (§6d-site, #6202/#6598/#8158)

Movido de `.claude/agents/orchestrator-stage-6.md` (#3445, orçamento de linhas por arquivo) — referência sob demanda, não carregada incondicionalmente.

**Branch dedicada + PR, nunca push direto em `master` (#6598).** Até 260828 este passo fazia `git commit` + `push` DIRETO em `master` — `.github/workflows/deploy-site.yml` documenta que `workers/site/public/p/**` é COMMITADO e o deploy real dispara por push a master, e publicar via `wrangler deploy` local deixaria o worker em produção divergente do repo, sem sinal (isso não mudou: continua descartado). O que mudou é o `master` em si: uma regra de proteção de branch (`GH013`) foi ativada nesse dia e passou a rejeitar todo push direto — o `push` que este passo fazia começou a falhar (`remote rejected`, exit `3` fail-soft, sem derrubar a edição, mas o acervo do site parava de crescer). Correção: o script agora recria `site-publish/{slug}` a partir do `master` local a cada chamada (`git checkout -B`), commita/empurra pra essa branch (`--force-with-lease`, seguro porque a branch é de propriedade exclusiva do script), e abre um PR via `gh pr create` — reusando um PR já aberto pra essa branch, se `gh pr list` encontrar um, em vez de duplicar.

**O script mergeia o próprio PR sozinho (#8158, 16/09/2026, revoga o #6598 acima).** A decisão original do #6598 ("o script NUNCA mergeia — mergear automaticamente foge do padrão branch→CI→merge desta linha de skills") foi revista: 12/12 PRs históricas dessa família mergearam sem problema, review automatizado rendeu ~zero achado (o diff é sempre 100% artefato gerado — `workers/site/public/p/{slug}/index.html` + 1 linha em `sitemap.xml`, nunca conteúdo com julgamento editorial), e Stage 6 já é o gate humano real. `waitAndMergeSitePagePr()` (`scripts/publish-edition-site-page.ts`) espera o CI convergir (poll de 5s, teto de 2min — folgado frente aos 19-44s medidos historicamente) e, se verde, `gh pr merge --squash` (sem `--delete-branch` de propósito — apagaria a branch local no checkout compartilhado fora da janela protegida pelo lock, #6626/#6703; `git checkout -B` recria do zero a cada chamada de qualquer forma) — reusa a mesma lógica pura de gate (`evaluatePrChecksGate`, #6225) que o merge autônomo do overnight/develop já usa. **Fail-soft, sem exceção**: CI vermelho, bloqueado por conflito, timeout, ou qualquer erro de `gh` faz o PR ficar aberto pra revisão manual — exatamente o comportamento único que existia antes do #8158, nunca um estado pior. Mesma categoria de isenção de review automatizado que o PR-trem/PR de resgate já têm (artefato mecânico, sem julgamento editorial — não precisa de `pr-review-toolkit:code-reviewer`).

`_internal/site-page-published.json` (#7283) ganhou o campo `merged` (`true`/`false`/ausente) — distingue "PR mergeado, deploy real vai acontecer no próximo push a master" de "PR aberto, esperando revisão manual" pra quem checar o estado depois do fato.

**Waiter em background e alerta de falha (#9593, #9616).** O job `test` leva ~12min, então a espera síncrona de 2min quase nunca vê o CI fechar; nesse caso o script dispara um waiter destacado (`--merge-pr N`, até 35min, `windowsHide`) que mergeia quando o CI fica verde e regrava `_internal/site-page-published.json`. Como o gate do Stage 6 quase sempre já foi aprovado quando o waiter termina, **todo desfecho sem merge** (CI vermelho, conflito, timeout, `gh pr merge` falho, state file ilegível) gera alerta por conta própria: `log-event` nível `error` em `data/run-log.jsonl` + `notifyEditor` `urgente` (issue de alarme `site-page-merge-waiter:pr-{N}`, família `evento`, P1; e-mail na criação). Idempotência: o `catch` do `gh pr merge` re-lê o estado do PR e trata `MERGED` como sucesso (merge concorrente de um 2º waiter ou do editor), e um `merged:true` já gravado no state file nunca é rebaixado por um waiter tardio. O merge usa `--match-head-commit` com o head cujo CI foi avaliado. **Lacuna conhecida:** waiter morto por reboot/kill não alerta (o processo não existe pra isso) — o state fica em "delegado" e só o invariante `site-page-pr-merged` (bloqueante desde #10160; era o warning `site-page-merge-pending`) de um re-run do Stage 6 acusa (check agendado pré-06:00 em #9621).

**PR aberto no início da Etapa 5, merge trava o fim da Etapa 6 (#10160, 14/10/2026).** O passo saiu do Stage 6 (§6b-site) e virou a 1ª ação do dispatch (§5b-site do `orchestrator-stage-5.md`): `publish-edition-site-page.ts --slug-from-d1 --sitemap workers/site/public/sitemap.xml --no-wait-merge`. `--no-wait-merge` reduz a espera síncrona a 1 poll (CI pendente vai direto pro waiter em background) e `--slug-from-d1` deriva o slug (`seoSlug` do título do D1, o mesmo link de WhatsApp do e-mail) antes de existir post. O state file ganhou `prNumber` e `status` (`open`/`merged`/`none`). No Stage 6, §6b-site só confere o PR (`scripts/check-site-page-pr-gate.ts`, sem espera; republica como fallback só sem registro), e §6c-site roda a mesma checagem com `--wait-ms 540000` ANTES do Schedule: MERGED segue, CI verde mergeia, vermelho/conflito/`gh` indisponível param com halt banner. Backstop: o invariante `site-page-pr-merged` (`severity: error`, sem `postDispatchOnly`) faz o `pipeline-sentinel.ts write --step 6` recusar o `.step-6-done.json` enquanto o PR registrado não estiver MERGED.

**Página defasada e bypass da trava (#10190, #10191).** A trava também recusa (exit `5`) a página cujo `slug` registrado difere do slug que o e-mail linka (`--expected-slug`, ou `seoSlug` do D1 atual) ou cujo `sourceDigest` (sha256 de `newsletter-final.html` + TÍTULO/SUBTÍTULO, gravado pelo publisher ao publicar) difere dos insumos atuais — o §5b-site congela os dois no início da Etapa 5 e o loop de fix do §5f/`kit-draft-fresh` pode mudar o D1 depois; §6b-site/§6c-site republicam pelo fallback e repetem. O invariante `site-page-pr-merged` aplica a mesma checagem de defasagem (`scripts/lib/site-page-staleness.ts`) mesmo com o PR já mergeado (#10207) — o backstop do sentinel cobre o §6c-site pulado; o slug esperado é o `--expected-slug` que a trava grava em `expectedSlug` no state, senão o do D1. `--bypass-reason "<motivo>"` transforma qualquer veredito ≠ merged em `bypassed` (exit 0) e grava `prGateBypass` no state; com ele, `site-page-pr-merged` e `site-page-published` caem pra `warning`. Uso: resposta `bypass` ao halt do §6c-site, ou automático no `--no-gates` (premissa: a newsletter não deixa de sair por causa da página).

# Mecanismo de publicação da página do acervo (§6d-site, #6202/#6598/#8158)

Movido de `.claude/agents/orchestrator-stage-6.md` (#3445, orçamento de linhas por arquivo) — referência sob demanda, não carregada incondicionalmente.

**Branch dedicada + PR, nunca push direto em `master` (#6598).** Até 260828 este passo fazia `git commit` + `push` DIRETO em `master` — `.github/workflows/deploy-site.yml` documenta que `workers/site/public/p/**` é COMMITADO e o deploy real dispara por push a master, e publicar via `wrangler deploy` local deixaria o worker em produção divergente do repo, sem sinal (isso não mudou: continua descartado). O que mudou é o `master` em si: uma regra de proteção de branch (`GH013`) foi ativada nesse dia e passou a rejeitar todo push direto — o `push` que este passo fazia começou a falhar (`remote rejected`, exit `3` fail-soft, sem derrubar a edição, mas o acervo do site parava de crescer). Correção: o script agora recria `site-publish/{slug}` a partir do `master` local a cada chamada (`git checkout -B`), commita/empurra pra essa branch (`--force-with-lease`, seguro porque a branch é de propriedade exclusiva do script), e abre um PR via `gh pr create` — reusando um PR já aberto pra essa branch, se `gh pr list` encontrar um, em vez de duplicar.

**O script mergeia o próprio PR sozinho (#8158, 16/09/2026, revoga o #6598 acima).** A decisão original do #6598 ("o script NUNCA mergeia — mergear automaticamente foge do padrão branch→CI→merge desta linha de skills") foi revista: 12/12 PRs históricas dessa família mergearam sem problema, review automatizado rendeu ~zero achado (o diff é sempre 100% artefato gerado — `workers/site/public/p/{slug}/index.html` + 1 linha em `sitemap.xml`, nunca conteúdo com julgamento editorial), e Stage 6 já é o gate humano real. `waitAndMergeSitePagePr()` (`scripts/publish-edition-site-page.ts`) espera o CI convergir (poll de 5s, teto de 2min — folgado frente aos 19-44s medidos historicamente) e, se verde, `gh pr merge --squash` (sem `--delete-branch` de propósito — apagaria a branch local no checkout compartilhado fora da janela protegida pelo lock, #6626/#6703; `git checkout -B` recria do zero a cada chamada de qualquer forma) — reusa a mesma lógica pura de gate (`evaluatePrChecksGate`, #6225) que o merge autônomo do overnight/develop já usa. **Fail-soft, sem exceção**: CI vermelho, bloqueado por conflito, timeout, ou qualquer erro de `gh` faz o PR ficar aberto pra revisão manual — exatamente o comportamento único que existia antes do #8158, nunca um estado pior. Mesma categoria de isenção de review automatizado que o PR-trem/PR de resgate já têm (artefato mecânico, sem julgamento editorial — não precisa de `pr-review-toolkit:code-reviewer`).

`_internal/site-page-published.json` (#7283) ganhou o campo `merged` (`true`/`false`/ausente) — distingue "PR mergeado, deploy real vai acontecer no próximo push a master" de "PR aberto, esperando revisão manual" pra quem checar o estado depois do fato.

**Waiter em background e alerta de falha (#9593, #9616).** O job `test` leva ~12min, então a espera síncrona de 2min quase nunca vê o CI fechar; nesse caso o script dispara um waiter destacado (`--merge-pr N`, até 35min, `windowsHide`) que mergeia quando o CI fica verde e regrava `_internal/site-page-published.json`. Como o gate do Stage 6 quase sempre já foi aprovado quando o waiter termina, **todo desfecho sem merge** (CI vermelho, conflito, timeout, `gh pr merge` falho, state file ilegível) gera alerta por conta própria: `log-event` nível `error` em `data/run-log.jsonl` + `notifyEditor` `urgente` (issue de alarme `site-page-merge-waiter:pr-{N}`, família `evento`, P1; e-mail na criação). Idempotência: o `catch` do `gh pr merge` re-lê o estado do PR e trata `MERGED` como sucesso (merge concorrente de um 2º waiter ou do editor), e um `merged:true` já gravado no state file nunca é rebaixado por um waiter tardio. O merge usa `--match-head-commit` com o head cujo CI foi avaliado. **Lacuna conhecida:** waiter morto por reboot/kill não alerta (o processo não existe pra isso) — o state fica em "delegado" e só o invariante `site-page-merge-pending` de um re-run do Stage 6 acusa (check agendado pré-06:00 em #9621).

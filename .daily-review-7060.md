## Defeito

`raceWindowVerdict` em `scripts/lib/pr-checks-gate.ts:394-414` (commit `e8733f04`, PR #7076) decide a janela de corrida comparando **dois timestamps fixos**:

```ts
const earliestStartedAtMs = Math.min(...startedTimestamps);
const gapMs = Math.abs(earliestStartedAtMs - pushedAtMs);
if (gapMs >= windowMs) return null;
return { verdict: "pending", ... };
```

`gapMs` não depende de `now`. `headCommittedAt` (do commit HEAD) e `startedAt` (do run) são imutáveis enquanto o rollup não mudar — então, uma vez que o run mais antigo tenha começado dentro dos 20s do push, o veredito é **`pending` para sempre**, em toda chamada subsequente do gate, mesmo horas depois com o CI já concluído e verde.

A docstring de `DEFAULT_RACE_WINDOW_MS` (`scripts/lib/pr-checks-gate.ts:258-272`) afirma o contrário — "o próximo poll do chamador … resolve sozinho assim que os checks genuínos aparecerem" —, mas nada no código faz isso: só um run NOVO com `startedAt` mais tardio ajudaria, e `Math.min` garante que o run antigo continue vencendo enquanto estiver no rollup.

Agravante: o teste `"lote com 1 check dentro da janela e 1 fora => ainda conservador (usa o MAIS ANTIGO startedAt do grupo)"` (`test/pr-checks-gate.test.ts:595`) trava esse comportamento — basta **um** check ter começado cedo para pinar o PR inteiro em `pending` indefinidamente.

## Cenário de falha

1. PR aberta; push do commit HEAD às `02:13:53Z`.
2. GitHub cria o primeiro run às `02:14:00Z` (gap de 7s — o próprio caso medido na #7060).
3. Todos os checks terminam `SUCCESS` às `02:22`.
4. `scripts/check-pr-checks-gate.ts` (que passa `headCommittedAt`, ver `scripts/check-pr-checks-gate.ts:124-125`) é chamado às `02:25`, `02:30`, `03:00`, …: `gapMs` continua 7s → `verdict: "pending"` em todas.
5. O PR **nunca** chega a `pass`: o auto-merge (regra do CLAUDE.md "review limpo + CI verde → merge") nunca é autorizado, e `scripts/lib/wait-pr-checks.sh` gasta o teto de vida inteiro antes de desistir.

Ou seja, o fix trocou um falso-vermelho raro (a corrida real) por um **stall determinístico** em qualquer PR cujo primeiro run tenha começado nos primeiros 20s após o push — o caso comum, não o excepcional, já que o GitHub costuma disparar o workflow em poucos segundos.

## Cobertura de teste ausente (#633)

Nenhum teste da suíte nova exercita "mesma rollup, avaliada depois" — todos os 8 casos da `describe` do #7060 fazem uma única avaliação. O teste de regressão que falta é exatamente esse: rollup com todos os checks `COMPLETED/SUCCESS`, `startedAt` 7s após `headCommittedAt`, e uma noção de "agora" bem posterior → deve resolver para `pass`.

## Direção sugerida

A heurística precisa de um terceiro sinal para poder expirar:

1. Passar `now` (injetável) e só aplicar a janela quando `now - pushedAtMs < windowMs` — a corrida só existe nos primeiros segundos; um poll feito minutos depois já não tem motivo para desconfiar. (mínima, preserva as asserções existentes)
2. Só desconfiar de check ainda `IN_PROGRESS`/recém-concluído, nunca de um rollup inteiramente `COMPLETED` cuja conclusão é bem posterior ao push.

Além disso, `Math.abs` trata como corrida também um run que começou **antes** do push (run supersedido de commit anterior ainda no rollup) — mais uma fonte de `pending` permanente.

## Prioridade: P1

Bug sem workaround que afeta produção atual: bloqueia o caminho de merge automático (trem, overnight, contínuo e sessão interativa) de forma silenciosa — o gate não erra alto, ele só nunca diz "pass". Não é P0 porque não corrompe nada publicado nem gasta dinheiro; é P1 porque não há como contornar sem editar o código (não há flag para desligar `headCommittedAt` no `check-pr-checks-gate.ts`).

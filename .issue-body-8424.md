## O defeito

`scripts/ads-test-watch.ts:460-462` grava o `watch-state` incondicionalmente depois do laço de notificação:

```ts
if (!isDryRun && nextWatchState !== watchState) {
  saveWatchState(nextWatchState, deps.watchStatePath);
}
```

Esse state guarda os **cursores de idempotência** do alarme: `religarBrevoTriggeredAt` (`markReligarBrevoTriggered`) e `apuracaoCompletedAt` (`markApuracaoCompleted`). `scripts/lib/ads-test-watch-state.ts:119` gateia o alarme em `triggerReligarBrevo: nowDateStr >= runState.religar_brevo && watchState.religarBrevoTriggeredAt == null` — ou seja, uma vez gravado, o aviso **nunca mais é emitido**.

Até o commit d7f2e6f5f (PR #8424) isso era seguro *por acidente do fluxo de controle*: `sendGmailMessage` **lançava** em falha de envio, `main()` rejeitava, e `saveWatchState` nunca era alcançado — a execução seguinte re-tentava. A migração trocou `deps.sendEmail` por `deps.notify` (`notifyEditor`), que é **fail-soft por desenho e nunca lança**. Agora um `notifyEditor` que falha em tudo (ex.: `gh` indisponível, `issue.action === "failed"`, push de e-mail falhando) devolve normalmente, o laço segue, e o cursor é gravado assim mesmo.

## Por que é confiança alta

A própria fatia da migração introduziu o helper para exatamente esta armadilha — `scripts/lib/editor-notify.ts` (`shouldPersistAlarmedState` / `notifyEditorResultReachedEditor`, commit d56222e81 / PR #8406), cuja docstring diz textualmente:

> O risco: `sendGmailMessage` **lançava** em falha de envio, abortando `main()` ANTES da gravação do cursor (...). `notifyEditor` **nunca lançam** (fail-soft por desenho), então gravar incondicionalmente depois deles congela o cursor mesmo quando NADA chegou ao editor, e o alarme se perde.

Todos os outros remetentes migrados aplicam o guard — `scripts/systemd-failed-units-alarm.ts:386`, `scripts/worker-drift-check.ts:518` e `:609`, `scripts/overnight-watchdog.ts:763`. `scripts/ads-test-watch.ts` (última fatia, d7f2e6f5f) é o único que **não** aplica.

## Cenário de falha concreto

Dia do `religar_brevo`: `plan.triggerReligarBrevo` abre, `nextWatchState = markReligarBrevoTriggered(...)`, `deps.notify(...)` falha (issue `failed` + e-mail não enviado), o log imprime "achado registrado (issue #?, action=n/a)", e `saveWatchState` grava `religarBrevoTriggeredAt`. No dia seguinte `triggerReligarBrevo` é `false` — o editor **nunca é avisado de religar a Brevo**. Mesmo caminho para `apuracao-success` (o relatório congelado existe, mas o aviso some) e para `apuracao-unusable`.

## Correção sugerida

Acumular o resultado de cada `deps.notify` e só persistir quando o alarme de fato chegou ao editor, reusando o helper que já existe:

- importar `notifyEditorResultReachedEditor` de `scripts/lib/editor-notify.ts`;
- no laço, marcar um flag `allReached = false` quando o helper devolver `false` para algum achado;
- condicionar `saveWatchState` a `allReached`.

(Se o critério deve ser por-achado ou global é detalhe de implementação; o invariante é: cursor de idempotência não avança quando a notificação correspondente não chegou.)

Teste de regressão obrigatório (#633): dublê de `notify` devolvendo falha de e-mail + `issue.action === "failed"` no caminho `religar_brevo` → `saveWatchState` não chamado; execução seguinte ainda emite o achado.

## Prioridade

**P1** — bug em produção sem workaround automático: perde permanentemente um alarme de severidade "urgente" (religar Brevo / apuração do teste 2608, ambos com dinheiro/CAC em jogo) sem nenhum sinal para o editor. Não é P0 porque só se materializa quando a notificação falha, que não é o caminho comum.
